01 / FOUNDATION

Clarity is part of care.

The interface must work for two people in very different situations: a donor looking for proof and an affected household looking for help. The experience should also let a reviewer verify an event without becoming the public home page.

01 / DONOR

See where funds are

Understand reserve, allocation, confirmed distribution, and the receipt behind each real transfer. Do not show a fixture as a chain event.

02 / HOUSEHOLD

Know the next step

See the affected area, eligibility reason, payout availability, and recovery path. Never require public identity exposure to understand a decision.

03 / OPERATOR

Approve with evidence

Review the source notice and any AI suggestion, inspect uncertainty, then explicitly activate a response. Suggested areas are not official approval.

Product truthExperience consequence
Funds exist before an emergencyLead with reserve readiness, then show active allocation without double counting.
Identity stays privateExplain verification in plain language and show only pseudonymous public records.
One household, one claim per eventShow the reason for a repeat rejection and the enforcement layer actually in use.
Real delivery has unresolved partnersMark baht payout, official feeds, and production verification as unavailable until proven.

02 / BRAND IDEA

Prepared, direct, accountable.

“Emergency money ready before disaster. Clear help when it counts.”

Positioning

ReliefVue is proposed as the public face of a pre-funded relief reserve and direct household assistance flow. The story is readiness and trustworthy decisions, not a token launch or generic donation marketplace.

Personality

Calm, precise, humane, and transparent. Urgent enough to act, restrained enough to trust.

What differentiates it
  • Funding can precede an event.
  • A human confirms the affected area before claims open.
  • Household eligibility is private; fund movements can be audited.
  • The same verified household cannot reuse a claim for the same event when enforcement exists.

Use “ReliefVue” as the working name selected for the prototype. Product, legal, and trademark clearance are not recorded.

Interim usage guidance

  • Keep the mark and name together in the prototype.
  • Use one solid ink color for lettering; avoid gradients and decorative effects.
  • Leave at least the mark’s width around the lockup in design studies.

Production gap

04 / COLOR

Calm surfaces. Clear action.

This palette extracts the coherent green direction already present in the latest prototype. Values are proposed interface colors, not approved brand inks or print conversions.

Focus amber#EB992EKeyboard focus ring

Role rules

Use white or near-white surfaces for long reading. Deep ink is the default text color. Action green is for deliberate actions and navigational emphasis. Mint is a support surface and must carry dark text.

State rules

Success uses green plus an explicit success message. Pending uses amber plus “pending.” Rejection uses a warm red surface and the reason in words. A status must remain clear without color.

The palette and its combinations are a review proposal. Contrast must be checked in every implemented text, control, and focus state before accessibility claims are made.

06 / VOICE

Tell the truth at every step.

Action

“Give help” / “Get help”

Use human intent on the landing view. At checkout, label disaster relief and optional platform support as separate destinations. Use the exact action, such as “Donate test SOL,” at the transaction point.

Eligibility

“Your recorded home is inside the approved response area.”

Explain why a result was reached, and what has or has not been verified.

Receipt

“Donation confirmed on Solana Devnet.”

Say this only after confirmation and link the actual signature. Otherwise show pending, failed, or preview.

Language to avoid

“Instant guaranteed aid.” “AI verified the disaster.” “All donations are on chain.”

These claims outrun the current product evidence. Distinguish planned capability, implemented code, observed transaction, and production service.

Seek

Everyday resilience, trusted local action, prepared supplies, clearly sourced geographic context, and real product evidence. Favor natural light, quiet composition, and subjects with agency.

Avoid

Unconsented disaster portraits, sensational damage, anonymous “victim” imagery, decorative blockchain coins, maps that suggest false area precision, and illustrations that imply verification has occurred.

08 / EXPERIENCE ARCHITECTURE

Two public journeys. One review route.

The first viewport should name the active or preparing response, then show giving and receiving as equally findable actions. Operator controls sit in a separate route with real authorization planned for production.

01OverviewReserve readiness, event state, Give help, Get help, Fund activity.
02Give helpRelief amount → optional platform support → separate totals → confirmation → real receipt or failure.
03Get helpProfile → area check → eligibility reason → available payout → receipt.
04OperatorNotice source → AI suggestion → uncertainty → human approval → activation.

Website pages

  • Public overview and current response
  • Give help
  • Get help
  • Fund activity and receipt detail
  • How it works / privacy and limitations
  • Operator route for authorized staff

Essential states

  • No active response; open; closed
  • Loading, empty, pending, confirmed, failed
  • Eligible, outside area, needs review, already received
  • Insufficient confirmed funds
  • AI unavailable, uncertain, awaiting human approval

Current GPS alone must not exclude a displaced household. Eligibility uses a verified home area in the intended product; current demo profiles are synthetic.

Responsive rule

Use a single column for task steps and event data at narrow widths. Keep Give help and Get help visible without horizontal scrolling. Let long addresses and signatures wrap without hiding the copy action.

Accessibility rule

Target WCAG 2.2 AA. Use labels, keyboard operation, visible focus, text status, and reduced-motion support. Test 320 px, 200% zoom, errors, long data, and real assistive technology before a conformance claim.
